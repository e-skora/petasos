## Blockers

### 1. Give ordinary writes and transaction-owned writes one expiry rule

blocker | `changes/002-memory-canary-guard/spec.md:25` | VERIFIED, REASONED | The supplied `put` wrapper cannot satisfy the required sweep behavior.

Sections 2.3 and 2.9 require every public store operation to sweep expired entries first. Section 2.4a makes `put_in` the explicit nonsweeping exception, but defines `put` as only a transaction around `put_in`. That wrapper never sweeps either. This changes behavior: overwriting an expired private key at T0 may either raise `TierLocked` against the old row or create a new public entry after the old row is deleted. Both outcomes follow different parts of the same document. Acceptance test 13 can pass by calling `read` first and never expose the disagreement.

**Fix:** State that ordinary `put`, `read`, and `search` sweep in their own transaction, while `put_in` neither opens a transaction nor sweeps. Specify how `put_in` handles an already-expired matching key. A simple choice is to replace that expired row within the caller's transaction, retain its old canary registry row, and treat the replacement as a new entry identity. State whether a failed write rolls back any sweep. Keep the connection-taking method; it is the right seam for atomic session seeding.

**Acceptance:** Use separate fixtures to overwrite an expired T4 key through `put` and through `put_in`, without any intervening read. Check entry identity, tier, old-token detection, and rollback of the caller's other seed writes. Include the exact expiry instant.

### 2. Bound actual scan and buffering work, not only selected containers

blocker | `changes/002-memory-canary-guard/spec.md:33`; `changes/003-mcp-server-helpdesk/spec.md:36` | VERIFIED, REASONED | The claimed guard bounds do not bound its accepted inputs or the response buffer.

002 accepts tuples, arbitrarily long strings and bytes, and a caller-supplied canary collection. Its item limit names only dictionaries and lists. A shallow, very large tuple or one huge string does not cross either written bound. Canaries deliberately survive entries forever, so 003's global set also grows beyond the 1,000-token performance fixture. Separately, 003 requires complete JSON bodies and SSE events to be parsed but gives neither buffer a byte limit. A stream without an event terminator can keep accumulating data. A one-second test for one chosen input does not settle any of these limits.

**Fix:** Name a cumulative node limit covering dictionaries, lists, tuples, keys, and values; an aggregate text/byte limit; and a bounded strategy for matching the retained canary registry. Exceeding a limit must give `guard_error`, never skip remaining content or truncate the token set. Give JSON bodies and individual SSE events explicit byte limits before allocation grows without bound. Preserve old-canary detection; do not solve registry growth by forgetting markers. Record the chosen thresholds in the spec so the builder need not invent them.

**Acceptance:** Test the limit and one over it for tuples, many small nested containers, text/bytes, JSON bodies, and unfinished SSE events. Test beyond the current 1,000-canary fixture, including an old token from an expired session. Pin whichever bounded indexing or refusal behavior the planning thread chooses.

### 3. Specify a private read-result channel that the existing Gate can support

blocker | `changes/003-mcp-server-helpdesk/spec.md:32`; `:33`; `:50` | VERIFIED, REPRODUCED | `result_json(gate.propose(...))` cannot return ticket data through the named interface.

`trust/outcomes.py` defines `Result` with only code, sentence, tier, verb, grant id, and scope. `trust/tools.py:43` defines an effect's return as an outcome string. `trust/executor.py:271-290` writes that return into ledger detail and returns a fresh `Result` with no payload. There is no data field for 3.18's ticket body, notes, mail, or refunds. The 003 wall forbids changing those trust files.

The executed probe registered a synthetic L1 read and called `Gate.propose`. Returning `"executed"` from the effect produced an ordinary result with no data. Returning `{"body": "synthetic-read-payload"}` still produced no data in the result, but copied that object into `ledger.detail_json.outcome`. `Ledger.verify()` returned `None`: a valid hash chain does not make retained visitor text acceptable. This demonstrates why returning data as an outcome is not a safe integration workaround; it is not a request to re-review 001's string-return contract.

**Fix:** Define the read bridge before build. Within the current wall, one option is a fresh, per-call result holder captured by the read effect: the effect reads on the executor's connection, captures a snapshot, and returns only `"executed"`. The adapter releases the captured snapshot only after a successful committed Gate result. No holder is shared across calls or sessions. Specify the `executed` to `ok` mapping and the collection resource/version behavior for `list_tickets`, which has no ticket argument. Alternatively, schedule an explicitly authorized additive trust-result change before 003; do not silently widen this build's wall.

**Acceptance:** A real MCP read returns the seeded data and one READ execution row. Force ledger append to fail after the effect captures data: no captured data may leave. Run concurrent reads of different sessions and verify the results and ledger contain no other session's text. Scan every ledger column, not just the hash chain.

### 4. Bind domain lookup callbacks to trusted scope explicitly

blocker | `changes/003-mcp-server-helpdesk/spec.md:35`; `:44`; `:48` | VERIFIED, REASONED | A scoped Gate does not pass its scope to the two lookup callbacks.

The planned `GateFactory(db, registry_of_tools, clock)` takes a registry, while `current_version(conn, "ticket:<number>")` and `resolve` must distinguish sessions whose ticket numbers overlap. Existing `Gate.propose` calls `definition.resolve(conn, validated)` at `trust/gate.py:58`. Existing `ToolDefinition.current_version` takes only a connection and resource string. Neither receives the Gate's scope. The effect can use `record.scope`, but that record is built only after resolution. The specification names no trusted binding for the earlier callbacks.

**Fix:** Define `build_registry` as creating callbacks closed over the authenticated scope, with the Gate factory creating or safely selecting that scope-bound registry. Resolve, version lookup, and effects must all constrain SQL by the same scope. Never add scope to caller-supplied arguments or use mutable process-global scope. This also gives finding 3 a place to define its per-call result holder.

**Acceptance:** Seed the same ticket number with different bodies, destinations, amounts, and versions in two sessions. Reads return each caller's own row. Refund records resolve the caller's own destination. Changing A's ticket invalidates A's approval but leaves B's approval valid. Interleave the calls to catch shared mutable state.

### 5. Make the guard decide before releasing each complete message

blocker | `changes/003-mcp-server-helpdesk/spec.md:36-37`; `:120-124` | VERIFIED, REASONED | The chunk rule and SSE parser are weaker than the promised response refusal.

SSE means server-sent events: one logical event can span several HTTP chunks and several `data:` lines. A copied 24-byte tail can detect a split token in the next chunk, but it does not retract bytes already sent from the first chunk. More seriously, privacy-key checking requires a complete decoded JSON value. Scanning each `data:` line separately and parsing only when it happens to be valid JSON can miss a valid multiline event. For example, an event can split its data into `{"private_notes":` and `"synthetic text"}` on separate data lines. Each line is invalid JSON; the combined event is valid and contains the forbidden key. Merely observing a later guard trip is not proof that the private payload was withheld.

The canary set is read only on the first body chunk. A long-lived stream can then miss a token minted after that snapshot. The expiry rule intentionally retaining canaries does not fix a stale snapshot.

**Fix:** Buffer and validate the complete bounded JSON body, or one complete bounded SSE event, before forwarding any of that unit. Join SSE data lines according to event framing and define malformed/incomplete data behavior. Recheck the canary registry for each emission unit, or use a cache whose refresh is tied to committed registry changes. Define when response headers are held. Before headers, return 409; after headers, emit a fixed safe termination event and close. Test those outcomes separately instead of demanding 409 for every stream failure. Do not buffer an entire indefinite stream.

**Acceptance:** Capture the actual downstream ASGI send messages, not just status or a seam-call count. Split a token and an escaped privacy key at every chunk position. Test multiline data, malformed/incomplete events, failure after an earlier clean event, and a newly minted marker after stream start. Assert no bytes from the rejected logical event reached the client, the connection terminates, and exactly one safe refusal is logged when storage works. Inject a ledger-write failure and confirm termination without recursive logging or original payload release.

The transport probe confirmed that current MCP responses use SSE and send `http.response.start` before their body. A future seam can delay that start, but the specification must say how. The probe does not demonstrate a finished guard.

### 6. Resolve the approval-verb contradiction without weakening proposal authority

blocker | `changes/003-mcp-server-helpdesk/spec.md:32-34`; `:113` | VERIFIED, REASONED | `approve(token, verb)` cannot pass reflection that prohibits `verb` on every registered adapter.

The contradiction also reaches ARCHITECTURE.md invariant 1, which says no caller-facing entry accepts a verb, while its approval flow and 001 explicitly compare a submitted verb. This is an existing wording conflict that 003 now turns into an impossible acceptance test. Renaming the argument or hiding it inside a dictionary would only defeat the test.

**Fix:** The planning thread should state the narrow distinction: proposal risk facts and derived verbs are server-owned; an authorized approval endpoint accepts a claimed verb solely to compare it with the stored grant. Align the governing wording in a planning edit and exempt only that approval comparison in the reflection test. Proposer and approver identity, scope, flags, and tier remain server-owned. Preserve the wrong-verb burn test.

**Acceptance:** Inject risk, tier, scope, and approver fields through actual MCP arguments and confirm rejection with no effect. Check that the approval's claimed verb cannot rewrite the stored grant or authorize a different action. Reflection is supplementary evidence, not the security boundary.

### 7. Do not retain caller-controlled URL paths in the ledger

blocker | `changes/003-mcp-server-helpdesk/spec.md:37` | VERIFIED, REASONED | The new ledger detail includes `route: path`, although a request path is caller-controlled text.

The seam covers unknown routes as well as registered routes. If scanning fails on a request to an arbitrary path, the specified guard-error row would preserve that path after session data is deleted. This conflicts with ARCHITECTURE.md invariant 11 and 001 section 1.22. Existing `ledger.append` accepts the supplied detail; it does not sanitize a route. Acceptance test 24 names bodies and secrets but does not exercise a visitor-supplied path.

**Fix:** Record a server-owned route label selected from a fixed allowlist, with a constant such as `unmatched` for everything else. Never store the raw path, query, headers, parse error, or rejected key. Add an injected clock to `GuardSeam` as well: its proposed constructor has no clock, but ledger append requires a timestamp and 3.26 requires clock injection.

**Acceptance:** Request an unknown path containing a synthetic marker with scanning forced to fail. Confirm the marker appears nowhere in the ledger and only the fixed fallback label is stored. Repeat with malformed authentication and no identity; do not derive an actor from the presented, unverified client id.

### 8. Replace impossible isolation and quota acceptance tests

blocker | `changes/003-mcp-server-helpdesk/spec.md:128`; `:130` | VERIFIED, REASONED | Two required results contradict the API they are meant to test.

Acceptance test 17 asks for session A's ticket 3 fetched as B to be refused. But both sessions deliberately have ticket 3, and the public API accepts only that local number. `get_ticket({"ticket": 3})` as B must return B's ticket 3. There is no A identifier in that request. A builder could make the test pass only by changing the numbering contract or adding an unsafe way to name another scope.

Acceptance test 19 asks the same session's calls to succeed again 61 minutes later. Its identities expire after 60 minutes and must return 401. Testing the limiter alone with an artificial longer-lived session is possible, but it is not the specified end-to-end acceptance test.

**Fix:** For isolation, use the distinct same-number rows in finding 4 and assert B's data is returned, never A's. Also test a number present only in A and reject any attempted scope argument. For quotas, test rolling-window replenishment directly at the quota-store layer with a synthetic scope; at HTTP level, an expired token stays refused and a newly minted session can call tools. State the layers in the spec, plan, and tasks.

## Should-fix findings

### 9. Make canary embedding stable when given previously stored text

should-fix | `changes/002-memory-canary-guard/spec.md:26`; `:90-94` | VERIFIED, REASONED | The update rule says to append the same marker whatever the new text says, but the invariant promises exactly one marker.

A caller can read a T4 entry and put its `Entry.text` back. Blindly appending makes two copies, while existing tests use only fresh text. An 8,192-character input also becomes longer than that after embedding, so writing the returned value back can fail unexpectedly.

**Fix:** Define whether the length cap applies to caller text or stored text. Choose either canonical normalization of the entry's own marker or explicit rejection of already-embedded input, and test it. Define replacement after expiry in terms of entry identity, as in finding 1. Keep old canaries and do not grant a downgrade merely because text changed.

### 10. Make binding-cache misses fail closed and retire bindings with sessions

should-fix | `changes/003-mcp-server-helpdesk/spec.md:25` | REASONED | Dropping the oldest identity binding does not necessarily end the SDK session it protected.

A live transport can outlast its entry after many other sessions are created and closed. The written mismatch check covers a present binding but does not explicitly cover a missing or evicted one. The SDK's own transport limits do not define this custom identity map's lifetime.

**Fix:** Reject every request carrying an MCP session id whose identity binding is absent, and require reinitialization. Remove bindings when the corresponding transport ends; do not silently treat an unknown binding as a new authenticated session. Prefer one lifecycle for binding and transport state.

**Acceptance:** With a small injected cache limit, keep one session live while other sessions churn, then present its id with both the original identity and a different identity after eviction. Neither may enter the SDK under an unbound id. Test POST, GET, and DELETE, plus identity expiry on an already-open transport.

### 11. Define quota admission and counter transactions, and test races

should-fix | `changes/003-mcp-server-helpdesk/spec.md:58-59`; `:131-133` | VERIFIED, REASONED | Sequential counts and source-text searches do not prove atomic limits or the stated counter semantics.

Specify one transaction for checking and reserving the last quota slot. Define whether `tool_calls` counts attempted, admitted, successful, or refused calls. A middleware admission and a later `Gate.propose` use different transactions under the existing interfaces; calling both one atomic tool-call event would be misleading. The 30-per-hour mint quota and 500-per-day ceiling both apply; returning at the first one without testing the second leaves daily admission unproved.

**Fix:** Count an admitted call together with its quota reservation, if that is the intended event, and document how later adapter failures affect the count. Keep session mint, its quota reservations, seed writes, and mint counter in one transaction. Keep a guard trip and its counter together when the ledger transaction succeeds. Do not change 001 transaction ownership. Add concurrent last-slot tests for calls and mints, daily-limit boundary tests, and an explicit cross-session abort test. Verify preserved global state by reading the database after cleanup. Searching for two SQL spellings cannot catch equivalent deletes, counter resets, or race conditions.

### 12. Prove raw MCP validation and consistent refusal shapes

should-fix | `changes/003-mcp-server-helpdesk/spec.md:26`; `:47`; `:115` | REASONED | Python signature tests and direct Gate tests cannot establish what reaches the Gate after SDK argument handling.

Typed adapters may validate or coerce arguments before domain validation. The spec also says every out-of-set tool returns `refused/not_allowed`, while acceptance test 10 expects a misspelled name to return `refused/unknown_tool` with a ledger row. Pick the order for unknown names versus known-but-forbidden tools. Refusals before an adapter, `recall`, and `ping` do not automatically receive the trust core's ledger behavior, despite 3.25's broad sentence about tool calls.

**Fix:** State strict wire-level behavior for extra keys, boolean or fractional ticket numbers, numeric amounts, zero refunds, and missing arguments. Decide which refusals and read tools are ledgered, using only constant codes and authenticated identity. Require valid MCP tool-result envelopes for middleware refusals, and plain sentences as well as statuses. Do not return an arbitrary status dictionary where the client expects an MCP `CallToolResult`.

**Acceptance:** Drive these cases through a real in-process MCP client, including forbidden tool calls and malformed requests, then inspect effects, grants, quota consumption, and ledger rows. Prove a middleware refusal is decoded by the client as the intended tool error rather than an invalid protocol response.

## What is sound and should be kept

- `put_in(conn, ...)` permits session, identities, tickets, and planted memory to commit together. Database transaction ownership and the two-line schema import approach match the existing storage module.
- Retaining canaries after entry or session deletion is correct. The guard must match tokens globally, including tokens originating in another scope. Retention must be paired with the bounded matching strategy in finding 2.
- The case-sensitive `private` / `private_` rule is a workable server-side naming convention, not a general secrecy detector. Do not broaden it into guessing from arbitrary words or treat it as permission to skip tier filtering. Scan decoded structured output as well as raw bytes.
- Bearer lookup by the presented id, digest comparison, expiry refusal, and separate `may_stage` and `approver` flags fit the intended model. The dummy comparison reduces one timing difference; it does not prove the entire database-backed authentication path has identical timing.
- The SDK middleware seam is viable. The executed probe saw the HTTP authorization header for initialize, tools/list, and tools/call, filtered a two-tool list to just `ping`, and completed a ping call. `call_next` returned a dictionary in this path; the first exploratory probe assumed a model object and failed, and the corrected dictionary handling succeeded. This is consistent with the pinned [official middleware contract](https://github.com/modelcontextprotocol/python-sdk/blob/v2.2.0/src/mcp/server/context.py), which permits models or dictionaries as results.
- Keeping the hidden ticket out of listings and write resolution while allowing direct get-by-number is a deliberate demonstration, consistent with PRODUCT.md. Its safety depends on the outbound guard and tests of actual delivered bytes.
- Exact approval tokens, server-derived destinations and amounts, current resource versions, and scoped grant operations can use the existing 001 interfaces. No new review of the settled core is needed to resolve the integration gaps above.
