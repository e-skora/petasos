## Remaining findings

### R1. Renewal must not reuse the session that just failed authentication

blocker | `changes/007-demo-app/spec.md:24` | REASONED from the revised rules and the existing reset contract.

The new rule applies to every mint: acquire the browser lock, re-read storage, and reuse a session whenever its saved expiry is more than 60 seconds away. But a current-session 401 must start a fresh session. After 005's operator reset, the browser still holds the original, future expiry while the server has expired the identity immediately. Renewal therefore encounters a supposedly fresh stored session and reuses the credentials that just failed. The current test demands another mint without defining how the reuse rule makes an exception. “Start over” also needs an explicit replacement rule under that same lock.

**Fix:** Pass the rejected or deliberately replaced session id into the locked operation. Reuse a valid stored session only if it differs from that rejected/replaced id. Otherwise replace that id once. Re-read inside the lock so a second tab can adopt the replacement already made by the first. Clear cards and cancel the initiating tab's active hold as well as those in other tabs. Test a 401 while the saved expiry is still 45 minutes away, two tabs receiving that session's 401 concurrently, and “Start over” on an unexpired session. Each replacement should mint exactly once and never reuse the rejected session.

### R2. The deployed workflow does not handle the new exit code as specified

should-fix | `.github/workflows/deploy-api.yml:108-112` and `changes/005-deploy-fly-cloudflare/spec.md:39` | VERIFIED, reproduced with the actual shell case block.

The revised specification treats smoke exit 4 as a warning with an explicitly unconfirmed release. The workflow still handles only 0 and 3 specially. Exit 4 reaches the default branch, records `SMOKE_RESULT=FAILED (exit 4)`, and fails the job. That is restrictive, not a false confirmation, but it contradicts the new release contract and directs an operator toward the failure/rollback path for an intentionally absent 004 route.

**Evidence:** Running the unchanged case block with `code=4` exited 4 and wrote exactly that failed result.

**Fix:** Add the planned exit-4 branch with an unconfirmed summary and warning, and test the workflow's handling of all five script exit codes. In 5.9 also change the stale permission text from `checks: read` to the actual `actions: read`, and say “newest run, which must be completed” rather than “newest completed run.” The new Python gate already rejects a running newest run correctly.

### R4. Align the rotation race test with the new lock-first algorithm

should-fix | `changes/005-deploy-fly-cloudflare/spec.md:104` | REASONED from the serialized transaction sequence.

Test 9 says that two rotation attempts in the same second make the second fail at exclusive archive creation. With the specified 25 rows, threshold 20, and the write lock now acquired first, the second attempt waits for the first to commit. It then sees one rotation-marker row, below the threshold, and must return `None` before opening a file. Both requirements cannot hold for that fixture.

**Fix:** Require one successful rotation and one no-op in the ordinary two-attempt race, with the first archive preserved and valid. Exercise the filename collision separately by restoring enough source rows to reach the threshold in that same clock second, or by pre-creating the target file with the source already above threshold. Preserve the broken-source case's expected bad-row result rather than applying the paragraph's blanket `verify() is None` assertion to it.

### R5. Make the receipt tests independent of which parallel build merges first

should-fix | `changes/005-deploy-fly-cloudflare/spec.md:109` and `:120` | VERIFIED comparison of the revised smoke test and unchanged reader test.

Test 11 now correctly distinguishes an absent receipt route from a stand-in route that reads the real fake-refund table. Reader test 16 still uses plain `build_app` and says the journey passes. On the allowed 005-before-004 build, the route is absent and the correct outcome is exit 4. Conversely, after 004 merges, `create_app` includes the real route, so a test that assumes the “003 app” lacks it cannot keep expecting exit 4 without explicitly arranging that condition.

**Fix:** Define the two test configurations explicitly: a receipt route forced absent, and a receipt route provided by the test stand-in or the real merged 004 implementation. Make reader test 16 use the receipt-enabled configuration for a full pass. These tests must retain their meanings when 004 merges, without changing a file outside 005's wall. State the live journey order as first approval, first receipt read, repeated approval, second receipt read.

### R6. Finish the fixture contract's coverage and required-directory check

should-fix | `changes/004-owner-api/spec.md:113` and `changes/007-demo-app/spec.md:28` | VERIFIED inspection of the named fixture map.

The named map and type checks are a substantial improvement. However, the only non-empty approval fixture contains refund and email cards; the deletion-card variant still has no live contract fixture. More importantly, the test continues to pass when `demo/src/fixtures/` is absent, regardless of whether the demo package exists. Removing the entire directory can therefore disable the promised server-side fixture check even after 007 is present.

**Fix:** Add a named deletion-card scenario and explicitly cover nullable card metadata. Use the existence of `demo/package.json` to decide whether committed fixtures are mandatory. When the package exists, an absent fixture directory or missing required file must fail. Add negative checks for that absence and the already-requested nested-field/type drift. Keep all of this in 004's test contract so 007 need not edit its forbidden server-test files.
