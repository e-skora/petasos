## 0. Terms used here

- **Session**: the three tokens and the expiry `POST /session` returns (003 spec 3.19). The app holds exactly one at a time, in memory and in `localStorage`, shared by every tab of the same browser so one visitor spends one mint per hour.
- **Role token**: the token of the current "You are:" selection (Owner, Agent, or Visitor). The app sends it on every read; ticket actions and the guided scenario always send the agent token (7.4).
- **Hold**: the press-and-hold gesture that approves a card: 1.2 seconds for L4, 2.5 seconds for L5 (D-009). The gesture works with a pointer or with the space bar.
- **Pill**: the "N waiting for you" indicator in the top bar. It has exactly three states: unknown, a number, or none waiting (D-014).
- **Guided scenario**: the "Ask for a $42 refund" walk-through on the home screen.
- **Recorded response**: a JSON file under `demo/src/fixtures/` with invented values in the exact key shape of one 004 endpoint response; 004's test 17 checks the key sets against the live API, so the app's tests never need a server.
- **Envelope**: the five-key JSON of 004 spec 4.6 (`status`, `explanation`, `tier`, `verb`, `grant_id`, plus `data`). The one other shape the app reads is the guard seam's `409` (003 spec 3.10), a JSON-RPC error object; `api.ts` maps it into an envelope with `status` `refused/guard_tripped` and `explanation` set to `error.message`.

## 3. Acceptance tests (plain language; each becomes a Vitest test named for it)

Every test runs under Vitest with jsdom, fake timers, and a fake `fetch` that replays recorded responses; no test touches the network, a real clock, or `dist/`.

1. Session: on first load with an empty `localStorage`, exactly one `POST /session` is sent even when three components ask at once (a counting fake fetch); the tokens land in `localStorage` with `expires_at`; a second load within the hour sends no mint; a stored session under 60 seconds from expiry is replaced by one mint; a `401` on a read mints once more and shows the "Your hour is up" line; a `429` from `POST /session` shows the recorded `explanation` and "Try again" and no further mint is sent until it is clicked; "Start over" sends one mint and clears the old tokens; no token string appears in `location.hash`, in any rendered text, or in any `console` call (spied).
2. Failure handling: a network error on `approve` shows "We could not reach the demo. Nothing is known to have happened; check the inbox." and triggers one approvals poll; a `429` on `propose` shows the recorded `explanation`; the inbox on a `403` shows the "We could not check" sentence and no list.
3. Hold timing, for both tiers: with the fake timers, a release at 1199 ms of an L4 hold cancels and at 1201 ms approves; an L5 hold does not approve at 1201 ms, cancels at 2499 ms, approves at 2501 ms; the timer alone at 5000 ms with no release approves nothing; the rendered button's `--hold-ms` is `1200ms` for L4 and `2500ms` for L5.
4. Hold cancels: `pointerleave`, `pointercancel`, a `pointerup` outside the button rectangle (mock `getBoundingClientRect`), `blur`, hidden `visibilitychange`, a repeated Space `keydown`, Enter, and a plain `click` each cancel or do nothing; a Space `keyup` after the window approves; Space `keydown` has its default prevented; the "Approve without holding" button is absent from the DOM until the disclosure opens, then approves on one click. `HOLD_MS` is the only place `1200` and `2500` appear in `demo/src/**` (grep at test time, excluding test files, pattern built at run time).
5. Pill: "?" for Visitor and Agent with no poll sent, a number for Owner with recorded cards, the none-waiting state only after a successful Owner poll returning an empty list, "?" after a failed poll; a poll is sent immediately after propose, approve, abort, and identity switch, and every 10 seconds while visible (fake timers and a counting fake fetch), and not while the document is hidden.
6. Guided scenario: with recorded responses, the six steps render in order; the propose sends the agent token and the approvals fetch sends the owner token whatever the switcher said before; with a recorded approvals list holding two cards, the shown card is the one whose `grant_id` matches; with a recorded waiting refund card for ticket 3, no propose is sent; the outcome step shows "Refund of $42.00 issued."; the ledger step lists only rows with that `grant_id`; with a recorded `refused/invalid_arguments` the scenario shows the `explanation` and the "Start over" offer.
7. Ticket page and canary: each of the four actions sends the agent token and the right `tool` and `arguments` (`amount` as a two-decimal string); Visitor sees no actions panel; the canary page's button requests `GET /owner/tickets/7` and, on a recorded `409` JSON-RPC body, shows the DESIGN.md 2.5 "Blocked." copy and a link to the ledger.
8. Rendering: every screen rendered with recorded data produces DOM text that contains no bearer token, no grant token, no `cn-` string, no raw verb (`ISSUE-REFUND`, `SEND-EMAIL`, `DELETE-TICKET`), no `L4`/`L5` code, no ledger `code` value, and no em dash; every tier is shown with a strip, a tinted header, and a text chip together; the L5 card shows "Cannot be undone"; the `SEND-EMAIL` card shows the record's body under the summary; a recorded note and a recorded mail body containing `<img src=x onerror=alert(1)>` and `**bold**` render literally (no `img` element, the asterisks present); the outcome sentences for `executed` by verb, `aborted`, and `refused/stale_resource` are the 7.3 sentences and every other status shows the recorded `explanation`.
9. Build: a Vitest test calls Vite's `build()` with `outDir` under a temporary folder and asserts every `src` and `href` in the produced `index.html` starts with `/demo/`; `tsc --noEmit` passes (CI's `npm run build` runs it).
10. Fixtures: every file in `demo/src/fixtures/` parses as JSON, contains `demo-token-not-real` wherever a token key appears, and contains no other string that looks like a bearer (`<id>.<secret>` with a dot) or a canary (`cn-`).
