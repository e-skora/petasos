## Ranked findings

### 1. blocker | .github/scripts/merge_gate.py:835 | A new base can still use old permission

**VERIFIED / REPRODUCED.** `main()` pins `main_sha` once. `gather()` restarts when the PR's base moves, but passes the original `main_sha` into every retry. It never requires the fresh PR's base SHA to equal that pin. The plan, proposal, grounding, and whole-file comparisons therefore remain tied to the old base even after a stable newer base is observed.

Probe: pin main at M1, then return a stable PR based on M2, with a head that contains M2. The proposal at M1 is ratified; the proposal at M2 has been returned to proposed. `gather()` reads the M1 proposal, `evaluate()` returns `ready=True`, and `_Run.merge()` sends its merge request. Evaluating the same facts with the M2 proposal correctly refuses them. This is not the ordinary behind-main case: the probe explicitly makes the head contain M2, so an up-to-date-branch requirement would not solve it.

**Fix:** require the fresh base to match the pinned main revision. If main moved, stop this candidate until a new scan, or restart the complete scan with fresh main, merged dependencies, authority files, comparisons, and evidence. Carry the validated base into the merge check and refuse a mismatch there too. Add a test where the head contains a newer main that revoked ratification, and another where the newer main changed the wall. Both must produce no merge request.

### 2. blocker | .github/scripts/merge_gate.py:1113 | The final check ignores other admission changes

**VERIFIED / REPRODUCED** for changed PR metadata; **REASONED** for late review results. The final GET checks only open state, draft, hold, and head SHA. It ignores the base branch, title, and required wall section even though `evaluate()` relies on all three. With previously ready facts, each of these fresh responses still sent a simulated merge request: base retargeted to `release`; body with its wall section removed; title changed to another change number. The expected head SHA does not reject any of those changes.

The final check also never refreshes CI or either review. In the new scan-all-then-merge ordering, an early candidate's evidence may be old by the time later candidates finish gathering. A newly dismissed sole review, a new blocker, or an in-progress rerun can therefore be ignored. This is a larger interval than the unavoidable gap between the last check and the merge request.

**Fix:** re-gather and evaluate the candidate immediately before merging, using the still-current trusted base from finding 1. Bind the merge to the validated base branch, change identity, head, repository, required body, current CI, and both reviews. Abort or restart on changes. Test retargeting, title/body changes, review dismissal, a new blocker, and a rerun that begins while another candidate is being scanned. Preserve expected-head merge protection and the final hold check. This does not claim that a GET can make a last-millisecond hold atomic.

### 3. blocker | .github/scripts/merge_gate.py:334 | Malformed forbidden walls still mean no restriction

**VERIFIED / REPRODUCED.** `_wall_forbidden_problems()` checks a few blank-line cases but does not validate the restriction's complete syntax. With expected wall `src/petasos/**`, each form below produced `wall_problems=[]`, an empty parsed forbidden list, and `ready=True` for a change to `src/petasos/mcp/server.py`:

```text
wall_forbidden: src/petasos/mcp/**
```

```text
wall_forbidden: `src/petasos/mcp/**
```

```text
wall_forbidden: plus these:

Do not touch `src/petasos/mcp/**`.
```

The first omits backticks, the second has an unmatched backtick, and the third continues as prose rather than a bullet after a blank line. The exact old blank-line probe is fixed, but the intended complete validation is not. These are controlled malformed-plan probes, not a claim that a current plan contains one of these bypasses.

**Fix:** define and enforce a complete wall grammar, preferably with one parser returning validated paths. Require an explicit accepted empty form; reject missing, unmatched, or unrecognized restriction text and ambiguous continuations. Preserve the current plans through explicitly supported syntax or a separately reviewed normalization. Add all three negative cases to the gate tests. A malformed restriction must never silently become an empty list.

### 4. blocker | .github/scripts/merge_gate.py:560 | Dismissing a blocker now erases its force

**VERIFIED / REPRODUCED, including comparison against current main.** Use two Codex reviews on the same head: one clean `COMMENTED` review and one `DISMISSED` review whose body starts with `blocker`. With no inline comments, the gate on `main` returns not ready; this PR returns ready. The new `codex_reviews_on_head()` filter is used both to establish completed-review evidence and to collect blocker bodies, so it removes the dismissed finding from consideration entirely.

Rejecting a dismissed review as proof of completion is correct. It does not establish a new policy allowing its findings to be forgotten. Neither D-018 nor this phase defines an authorized dismissal or supersession rule, meaning a rule for when one review replaces another. The current new test for a dismissed review beside a clean review covers only an empty dismissed body.

**Fix:** separate positive completion evidence from blocker collection. Keep the old conservative treatment of current-head blocker bodies while requiring a supported submitted review for completion. Add the two-review regression above, plus the equivalent case with a retained thumbs-up completion signal. Any policy that lets dismissal clear a blocker needs separate approval and exact evidence rules; it is not part of a stricter-only repair.

### 5. should-fix | .github/workflows/claude-builder.yml:90 | Settled flags lack a complete recovery path

**REASONED from the prompt and AGENTS.md:42-53.** The new paragraph says to find an answer, note it, and set `BUILT`. It must also require applying that answer and testing the resulting work. An answer choosing a different schema or name does not mean the existing implementation already meets that choice.

The recovery paragraph is under step A, which selects only non-draft PRs at line 66. The stop-and-flag rule requires a draft, and the new paragraph turns any remaining unsettled case into a draft. Once planning supplies the answer, no defined step returns that PR to the repair path. The draft's presence also prevents step C from starting a replacement build. Further, only judgment-call flags currently receive question IDs under AGENTS.md item 3, while the new wording says every flag has an ID.

**Fix:** say explicitly that the builder cannot author its own settlement; it must read a planning-approved answer merged on main, implement any required change within its wall, and rerun the required checks before `BUILT`. Preserve `BLOCKED` for incomplete or out-of-wall work. Give every recoverable flag an ID or define how non-question flags are handled. Define the planning action that resumes a settled draft, or a narrowly authorized recovery path for those drafts. Do not resume held or repair-exhausted drafts merely because an answer exists. Add a walkthrough from draft flag through answer, implementation, tests, and fresh reviews.

### 6. should-fix | .github/scripts/merge_gate.py:614 | Codex is still asked on ineligible builds

**VERIFIED / REPRODUCED.** With green CI and no Codex review, `should_request_codex()` returns true separately for a missing dependency, invalid grounding, malformed wall, and failed Claude review. It checks a subset of eligibility rather than whether Codex is the sole gap. This wastes reviews that cannot yet enable a merge and contradicts the helper's stated purpose.

The caller also uses facts gathered before scanning other candidates. A hold added during `gather()` appears in its second GET but is discarded because the SHA pair is unchanged. The final merge check catches that hold if it remains, but the earlier Codex-request path has no equivalent recheck.

**Fix:** request only when the complete current verdict has no reason other than missing Codex evidence, or define and test a deliberately narrower allowed waiting set. Revalidate metadata and eligibility immediately before posting the request. Keep the new author check that prevents an ordinary copied comment from suppressing the request.

### 7. should-fix | .github/scripts/merge_gate.py:679 | A moving head becomes a fault during the wait

**VERIFIED / REPRODUCED.** The initial scan catches `PullKeptChanging` separately and treats it as waiting. During `wait_for_codex_many()`, the same exception enters the generic exception handler and is returned as an error, which `main()` counts as a controller fault. A fake clock and a `gather()` that raises `PullKeptChanging` reproduce this difference.

**Fix:** give the polling path the same ordinary-waiting treatment, without making the older saved facts eligible for a merge. Keep actual read, comment, merge, and cleanup failures as faults. Add a regression for moving heads during the Codex wait, not only during the first scan.

## Answers to the requested judgment calls

- **The five original probes:** all corrected at the reviewed head. Running Claude review is reported as running; the original blank-line forbidden wall is refused; a sole dismissed Codex review is insufficient; a draft does not trigger a Codex request; and a hold already present in the first fresh PR GET is respected. These narrow passes do not resolve findings 1 to 4.
- **Snapshot consistency:** fresh first-read metadata and head/base-change retries are improvements. They do not make all API responses one atomic snapshot. Main remains separately pinned, second-read metadata is discarded, and review states can change without either commit changing. Findings 1 and 2 address avoidable gaps. A hold placed after the last validation still requires a separately defined enforcement policy if absolute cancellation is required.
- **Parenthetical backticks:** acceptable for the current expected-path bullets. Inspection and the suite confirm that only the first path is admitted; the trailing parenthetical does not add paths. This alone does not require rewriting plans 002 and 003. Parenthetical content restrictions remain instructions for the builder and reviewer, not restrictions enforced by a path-only wall. Keep malformed syntax rejected, as in finding 3.
- **A constantly moving head:** ordinary waiting is the right classification, provided it never reuses older facts to merge. Implement it consistently in the polling path, as finding 7 requires.
- **No new Codex requests after a merge:** sensible for a run pinned to the previous main. Deferring until a fresh scan is safe. The statement that every other head must now be behind is stronger than necessary, since another worker could already have synchronized it. The remaining candidates' posted statuses also use pre-merge verdicts, so they may omit the new need to sync. Either refresh those facts or explicitly say they need a fresh evaluation; do not describe stale facts as current.
- **Stable flag IDs:** useful. Reading answers from main preserves the intended separation between builder and planning. Finding 5 names the missing implementation and resumption steps.
- **Stale claims:** the count-plus-three-dot-diff condition is a conservative improvement for preserving file work. Executed in a disposable local Git repository: an empty claim behind a newer main qualifies; a branch with work does not; work followed by a revert still does not, because it has multiple commits. The condition alone does not prove the commit is actually a claim, so also verify the stated claim identity. Fetch current refs and condition deletion on the inspected branch tip so a concurrent push cannot be deleted. Prompt text is not deterministic enforcement; no real branch was deleted in this review.
