## 0. Terms used here

- **Identity**: one authenticated caller: an id, a role (`visitor`, `agent`, or `owner`), a secret, a memory ceiling, a `may_stage` flag, an `approver` flag, and the session (scope) it belongs to.
- **Bearer string**: what a client sends in `Authorization: Bearer <id>.<secret>`. The id before the first dot is the presented client id; the lookup is keyed by it, so a secret replayed under another id fails (ARCHITECTURE.md invariant 17).
- **Visitor session**: three identities (one per role), one scope, one hour of life, its own fictional tickets and memory. Minted by `POST /session`. The scope is the session id and is the `scope` every 001 and 002 store is built with.
- **Session binding**: the record, kept by the identity middleware, of which identity initialized a given MCP session id (the transport's `Mcp-Session-Id`). A request on a session id with no binding, or with a different identity, is refused.
- **Guard seam**: the one ASGI layer through which every HTTP response passes on its way out. It releases a response only one complete, scanned unit at a time. Only the routes in `UNGUARDED_ROUTES` skip it.
- **Emission unit**: what the seam scans and releases as a whole: a complete JSON body, or one complete server-sent event (SSE, the framing the MCP streamable transport uses: lines up to a blank line; the event's data is every `data:` line joined with newlines).
- **Adapter**: an MCP tool whose body only maps the call to `Gate.propose` (or, for owner tools, to `GrantStore` and `Executor`) and maps the `Result` to JSON. Adapters never compute risk, tier, verb, or approver; the one claimed verb an adapter accepts is the approval comparison in 3.7.
- **Read capture**: a per-call holder that a read tool's effect fills with the data it read on the executor's connection, and that the adapter releases only after the Gate reports a committed `executed`. The trust core's `Result` carries no data field, and this change may not change it.
- **Scope-bound registry**: the `ToolRegistry` built for one authenticated scope, whose `validate`, `resolve`, `effect`, and `current_version` callbacks are closures over that scope, so every SQL statement they run is constrained to it.
- **Canary ticket**: one hidden ticket per session whose body is a T4 memory entry, so it carries a canary. It never appears in listings; fetching it by id returns the canary in the body, the seam trips, and the response is stopped.
- **Global ceiling**: an abuse counter across all sessions that a data reset never clears.

| 3.9 | Guard seam | `mcp/guard_seam.py`: `GuardSeam(app, db, clock)` is raw ASGI middleware installed as the outermost application middleware, so it sees every response the application produces. Starlette's own `ServerErrorMiddleware` sits outside it and answers an unhandled exception with its fixed text `Internal Server Error` and no application data; that page is the only response not scanned, and a test asserts its body is that constant. `UNGUARDED_ROUTES = frozenset({"/healthz"})`; a test enumerates every route the app registers and fails if any route outside that set is not wrapped (invariant 15). The seam never forwards a byte of a unit before that whole unit has been scanned: it holds the downstream `http.response.start` message and buffers body chunks until it has one complete emission unit. For a non-stream response (any `content-type` other than `text/event-stream`) the unit is the complete body, `MAX_BODY_BYTES = 1_048_576` (1 MiB). For `text/event-stream` the unit is one SSE event: bytes up to and including the first blank-line terminator, where a line ends with `\r\n`, `\n`, or `\r` (the transport uses `\r\n`), `MAX_EVENT_BYTES = 262_144` (256 KiB); the `data:` lines (with one optional space after the colon removed) are joined with `\n` per SSE framing; a comment-only event (`: ping`) is a unit too, scanned as bytes and forwarded. A stream that ends while `http.response.start` is still held and no unit was ever completed (a standalone GET stream closed before its first ping) releases the held start with an empty body end, so the response completes. The 002 node bound (`MAX_NODES`) applies to the parsed structure; a body under 1 MiB that exceeds it is a `guard_error`. The canary set is read from `canaries` for every unit through a cheap version check (`SELECT max(id) FROM canaries`; rebuild the `CanarySet` with `all_canaries` only when it changed, so 002's validation runs once per registry version), so a token minted after a stream started is still caught. Crossing a byte limit, an event that never terminates within the limit, a non-empty incomplete trailing event at stream end, or any exception inside the seam is a hit of kind `guard_error`. The seam never buffers more than one unit and never buffers an indefinite stream. Only after a unit passes are the held `http.response.start` (first unit) and that unit's bytes sent downstream. | Invariants 13, 14, 15. Finding 5: decide before releasing, on complete units, with a live registry. |
| 3.10 | On a hit | If `http.response.start` is still held (the hit is in the first unit): send `409` with `content-type: application/json` and the body `{"jsonrpc": "2.0", "id": null, "error": {"code": -32603, "message": <the Hit sentence>, "data": {"status": "refused/guard_tripped"}}}`, which the pinned MCP client copies through as a JSON-RPC error carrying the sentence, and stop; a non-MCP route (`/session`) gets the same body. An unsolicited GET stream has no pending request, so its termination is only a closed stream; no test may treat that as proof that a tool call received the error. If that transaction fails, the response is still terminated as above and the failure is logged to the process log only, once, with no payload; nothing retries into the seam. | Invariant 14; invariant 11 and 001 spec 1.22 (no caller text in the ledger). ## 2. Public interface

```python
from petasos.storage import Database
from petasos.app import create_app
from petasos.sessions import SessionStore
from petasos.mcp.guard_seam import UNGUARDED_ROUTES

db = Database(tmp_path / "petasos.sqlite")
db.migrate()  # ledger, grants, rail slots, memory, helpdesk, sessions, quotas, counters
app = create_app(db, clock=clock)

# A visitor mints a session (the README's one command in 006 is: curl -X POST https://api.petasos.io/session)
r = client.post("/session")  # 201: tokens for visitor, agent, owner (the owner is a simulation)

# As the agent, over MCP with Authorization: Bearer <agent token>:
#   tools/list  -> ping, list_tickets, get_ticket, recall, add_internal_note, reply_to_customer, issue_refund, delete_ticket
#   get_ticket {"ticket": 3} -> {"status": "ok", "data": {"number": 3, "body": "...", ...}}   (one READ ledger row, no data in it)
#   issue_refund {"ticket": 3, "amount": "42.00", "currency": "USD"}
#     -> {"status": "staged", "tier": "L5", "verb": "ISSUE-REFUND", "grant_id": 1, "explanation": "..."}   (no token)
#   list_pending_approvals -> isError, {"status": "refused/not_allowed", ...}
# As the owner:
#   list_pending_approvals -> {"status": "ok", "data": [{"grant_id": 1, "token": "...", "verb": "ISSUE-REFUND", "record": {...}}]}
#   approve {"token": "...", "verb": "ISSUE-REFUND"} -> {"status": "executed", ...}  (helpdesk_fake_refunds has one row)
#   approve the same token again -> {"status": "refused/unknown_or_used_or_expired", ...}
# As anyone:
#   get_ticket {"ticket": 7} -> 409 {"status": "refused/guard_tripped", ...} from the seam, and one ledger row
```

Signatures this change adds or changes (000's `build_mcp_server` keeps its name and gains parameters): `build_mcp_server(*, db: Database, clock) -> MCPServer` (registers every tool and the `ServerMiddleware`); `GateFactory(db, clock)` with `for_call(identity, capture) -> Gate`; `ReadCapture()` with `data`; `build_registry(db, *, scope, clock, capture) -> ToolRegistry`; `seed_session(conn, db, scope, clock) -> None`; `SessionStore(db, *, clock)` with `mint() -> Minted` (session id, expiry, the three bearer strings) and `expire(now) -> int` (sessions removed); `session_routes(store) -> list[Route]`; `reserve(conn, *, scope, family, limit, window, now) -> bool`; `ClientRegistry(db)`; `IdentityMiddleware(app, registry, clock, *, max_bindings=10_000)`; `GuardSeam(app, db, clock)`; `tool_result(result, data=None) -> CallToolResult`. `petasos.mcp.__init__` exports `build_mcp_server`, `IdentityMiddleware`, `ClientRegistry`, `Identity`, `GuardSeam`, `UNGUARDED_ROUTES`, `GateFactory`, `tool_result`. `petasos.helpdesk.__init__` exports `HELPDESK_SCHEMA`, `build_registry`, `seed_session`, `ReadCapture`. `petasos.sessions.__init__` exports `SESSIONS_SCHEMA`, `SessionStore`, `session_routes`, `reserve`, and the four limit constants.

## 3. Acceptance tests (plain language; each becomes a test named for it)

Every test builds its own app on a `tmp_path` database with the frozen clock and drives it through Starlette's `TestClient` or the pinned `mcp` client over streamable HTTP in process, as `tests/test_app_mcp.py` does today. "Through MCP" below means a real in-process MCP client call, decoded by that client.

Identity and middleware

1. `POST /mcp` with no token, with a malformed bearer (`no-dot`, `.`, `id.`), with a wrong secret, with the right secret under another session's client id, with an expired identity, and with a valid token plus any `Origin` header: each returns 401 with an empty body, and the MCP ASGI app was never called.
2. Three MCP sessions initialized with the visitor, agent, and owner tokens of one session list exactly the tool sets in 3.4, and `ping` works for all three.
3. A request on an MCP session initialized with the agent token but sent with the owner token is refused with 401; so is a POST, a GET, and a DELETE that carry an `Mcp-Session-Id` the middleware never bound. With `max_bindings=2` injected, keep session A's transport open, initialize two more sessions so A's binding is evicted, then present A's session id with A's original identity and with another identity: both are refused, and after A initializes again its calls work. After A's identity expires (clock advanced 61 minutes) a request on A's open transport is refused and its binding is gone.
4. `authenticate` runs `compare_digest` exactly once for a missing id and once for a present id (patch it and count); a missing id and a wrong secret both return `None`.

Adapters and responses

5. Through MCP, `issue_refund` as the agent returns `staged`, tier `L5`, verb `ISSUE-REFUND`, a `grant_id`, `isError=false`, and no key named `token` anywhere in the response (deep scan); `list_pending_approvals` as the agent is an `isError=true` result with `refused/not_allowed` and a plain sentence; as the owner it shows the grant with its token and a record whose `amount_minor` is 4200 and `currency` is `USD`.
6. Owner `approve` with the right token and verb returns `executed`; `helpdesk_fake_refunds` has one row for the grant, the ticket's version rose by one, and the grant is `EXECUTED`. The same `approve` again is `refused/unknown_or_used_or_expired` and `helpdesk_fake_refunds` still has one row.
7. Right token, wrong verb, burns the grant (`refused/verb_mismatch`, then the right verb is refused too); `approve` from the agent is `refused/not_allowed` and the grant survives; the owner cannot approve a grant the owner proposed (`refused/self_approval`). A claimed verb can never rewrite the stored grant: after a wrong-verb attempt the grant row's `verb` is unchanged, and no approve with any claimed verb executes a different tool than the record names.
8. No registered tool's signature has a parameter whose name contains risk, tier, flag, approver, or scope; `verb` appears only on `approve` (reflection over every registered tool); `create_app`'s signature has no `tokens`. Through MCP, arguments carrying extra keys named `risk`, `tier`, `scope`, `approver`, or `proposer` on `issue_refund` and on `approve` are refused by the middleware with `refused/invalid_arguments`, with no grant, no effect, no approval, no ledger row, and no quota consumed.
9. `reply_to_customer` as the agent stages an L4 `SEND-EMAIL`; six in one hour: the sixth is `refused/rail_full`. `add_internal_note` executes at once (`executed`, L2) and bumps the version; `delete_ticket` stages an L5 `DELETE-TICKET`; `list_tickets` and `get_ticket` return `ok` with the seeded data, and each writes exactly one `executed` ledger row with verb `READ` whose `detail_json` holds no ticket field.
10. Through MCP, each of these is refused with no grant and no effect, and the client decodes each as an `isError=true` tool result: shape refusals from the middleware (a missing argument, an extra key, `ticket: true`, `ticket: "3"`, `ticket: 3.0`, `ticket: 3.5`, `amount: 42` as a JSON number) give `refused/invalid_arguments` with no ledger row and no quota consumed; value refusals (`ticket: 0`, `"4200"`, `"42.0"`, `"42.001"`, `"0.00"`, a currency other than `USD`, an amount above the ticket's, an unknown ticket number, ticket 7 (hidden) on a write tool, a deleted ticket) give `refused/invalid_arguments` with exactly one `refused` ledger row and one `calls` quota event each; a misspelled tool name gives `refused/not_allowed` with no ledger row and no quota event. `abuse_counters.tool_calls` and the session's `quota_events` are read after the whole list and equal the number of value refusals.
11. After `issue_refund` is staged, a note is added to the same ticket (version bumps); the owner's `approve` then returns `refused/stale_resource`, the grant is `REJECTED`, and no refund row exists.
12. Read capture: with `ledger.append` patched to raise only when `kind == "executed"` (the executor's failure row must still be written) after `get_ticket`'s effect has filled its capture, the response is a `failed/execution_error` result with no `data` key and no ticket text anywhere in it; the effect's read left no row anywhere. Twenty `get_ticket` calls from two sessions, ten each, run concurrently on threads against one app, each return their own session's body, and no ledger column of any row contains either body.

Scope binding

Two sessions each have ticket 3 with different bodies, customers, and emails (the seed embeds the session id, 3.13); the test then sets B's ticket 3 `amount_minor` to 5000 by a direct row update so the amounts differ too. `get_ticket {"ticket": 3}` as B returns B's body and never A's; a ticket number present only in A (delete it in B first) is `refused/invalid_arguments` from B; `get_ticket {"ticket": 3, "scope": "<A>"}` is refused by the middleware as an extra key. `issue_refund` on ticket 3 in both sessions resolves each session's own email as destination and own amount (4200 and 5000 in the two records).
