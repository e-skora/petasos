## 0. Terms used here

- **Entrypoint**: `python -m petasos.serve`, the one command that starts the deployed process. Environment variables are read in exactly three places in `src/`: `serve.main`, the maintenance command line (through the same settings function), and 003's `app.py` `__main__` block, which stays as it is. `create_app` stays pure (003 spec 3.26).
- **Maintenance tick**: one run of `run_maintenance`, every 60 seconds inside the server process: delete expired visitor sessions, rotate the ledger when it is long, prune old archives.
- **Rotation**: moving every ledger row into an archive file and starting the chain again from a row that names the archive and its last hash, so `verify` stays fast and the history stays checkable.
- **Reset**: an operator command that expires every visitor session and every identity at once and lets the normal expiry path delete their data, in the normal order, so a reset that stops halfway leaves the same state as an ordinary expiry that has not been cleaned up yet.
- **Smoke journey**: `scripts/smoke_journey.py`, a script that runs the v1 promise against a running server over MCP: mint a session, read ticket 3 as the agent, propose the $42.00 refund, list and approve it as the owner, confirm it executed once. The release workflow runs it after every deploy; it is also the rollback check.
- **Release**: one run of the `Deploy API` workflow, started by hand with one exact commit (D-015). A rollback is a release of the previous known-good commit.
- **Edge**: Cloudflare, in front of `api.petasos.io` (DNS proxied), where the per-IP rate limit lives.
- **ASGI**: the Python web server interface every layer here speaks; a "raw ASGI layer" is a small wrapper that sees every request and response as messages.

| 5.7 | Ledger rotation | `rotate_ledger(db, *, archive_dir, now) -> RotationReport(archive: Path, rows: int, first_id: int, last_id: int, last_hash: str) \| None`. Everything happens inside one `db.transaction()` (`BEGIN IMMEDIATE`, taken first, so the count, the copy, the checks, and the delete all see one frozen table and no row can be appended meanwhile): it reads `count(*)`; below `LEDGER_ROTATE_ROWS` it returns `None` with nothing written. Otherwise the archive path is `archive_dir / f"ledger-{now.astimezone(UTC):%Y%m%dT%H%M%SZ}.sqlite"`, created exclusively (`open(path, "x")`, so a concurrent manual `rotate` and the tick can never share a file; if it exists the function raises and touches nothing); the schema is `LEDGER_SCHEMA` from `petasos.ledger.store` executed on a plain `sqlite3` connection with `row_factory = sqlite3.Row` (never `Database.migrate`, which would create every other table, and never `ATTACH`: a transaction that spans two files is not atomic under WAL). Copy: read the rows `ORDER BY id` in batches of `ROTATION_BATCH_ROWS` through a cursor (never `fetchall` of the whole table) and write each batch, unchanged, into the archive through its own connection in one archive transaction, while feeding every copied column of every row, ids included, in order, into a running SHA-256 digest of the canonical JSON of each row (`ledger.chain.canonical_json` or the same rule); commit the archive. Check, still inside the main lock and before any deletion: (a) read the archive back `ORDER BY id` and compute the same digest; it must equal the source digest (so an altered middle row, an altered id, a missing row, or an extra row is caught, which count-and-last-hash alone is not); (b) `chain.verify` on the archive connection must be `None` and `chain.verify` on the main connection must be `None` (an already-broken source chain is never laundered into a clean live chain by rotating it); (c) `count(*)` and the highest id's `hash` must match. Any failure raises, the main transaction rolls back with every row in place, and the `finally` removes the archive file this attempt created (only that file, by the path it opened exclusively; never another attempt's). Only after all three checks pass: `DELETE FROM ledger`, then `petasos.ledger.chain.append(conn, now=now, kind="maintenance", scope="global", actor="system", verb=None, tier=None, grant_id=None, record_hash=None, detail={"code": "rotated", "archived_rows": n, "archived_first_id": a, "archived_last_id": b, "archived_last_hash": h, "archive": <file name only>})` on the main connection, and the main transaction commits. The tick records `rotate` in `errors` on any raise and backs off (5.5). A crash between the archive commit and the main commit leaves the rows in place and a full archive on disk, which the next successful rotation duplicates under a later name (a harmless duplicate that pruning removes). The write lock is held for the copy and the checks; at `LEDGER_ROTATE_ROWS` 10,000 that is well under a second on local disk (measured for five times as many rows), and `docs/deploy.md` states that a rotation can delay one health check by a second or two on the platform's slower disk. Because the table is empty when `append` runs, the new row's `prev_hash` is the genesis hash and `verify()` is `None` afterwards; because `ledger` uses `AUTOINCREMENT`, ids keep rising across a rotation and never repeat (verified). The archive verifies on its own, and its last row's `hash` equals the new row's `archived_last_hash`, which is how a reader checks the join. What a rotation means for a visitor: the live table then holds only rows written after it, including for sessions that are still running, so 004's ledger view and verify report the marker's id as `archived_before_id` and the demo app tells the visitor that older rows were archived (004 spec 4.5, 007 spec 7.3); the ledger shown in the browser is the live segment, by contract, and `docs/deploy.md` says so. | ARCHITECTURE.md section 6 ("the exact retention, rotation ... are specified in change 005"); invariant 11 (the chain is never silently rewritten: a rotation leaves a row that names what moved and where, and never moves rows it has not verified). |

## 3. Acceptance tests (plain language; each becomes a test named for it)

Every test uses a `tmp_path` database and the frozen clock. `tests/support_005.py` holds the shared helpers: a lifespan harness that runs the whole ASGI `lifespan` call in one task (the MCP session manager uses a task group), sends `startup`, awaits `startup.complete`, and later sends `shutdown`; a tick gate (an `asyncio.Event`-based `sleep` passed to `MaintenanceRunner`) that releases exactly one tick per call; and a recording ASGI app. Nothing sleeps for real, nothing opens the network, nothing builds a container image.

The process

1. `settings_from_environ` with `PETASOS_DB` set gives that path, an archive folder beside it, host `0.0.0.0`, port 8080; with `PETASOS_ARCHIVE_DIR`, `PETASOS_HOST`, `PETASOS_PORT` set, those values; with `PETASOS_DB` missing or empty, or `PETASOS_PORT` not an integer or out of range, `SettingsError` with a one-line message; it never reads `os.environ` (a test passes an empty mapping while `os.environ` holds `PETASOS_DB` set to a marker path, and asserts the error). `main()` with `os.environ` patched to lack `PETASOS_DB` returns 2 and prints the message to stderr (`capsys`).
2. `build_app` creates the database file's folder and the archive folder, migrates (every 003 table exists afterwards), and returns an app whose `app` attribute is a `MaintenanceRunner` whose `app` is the FastAPI app; a `POST /session` through it (lifespan harness) is `201`; `python -m petasos.serve --check` in a subprocess with `PETASOS_DB` under `tmp_path` exits 0, prints `check ok`, creates the database file, and binds no port (the subprocess ends within the test); with `uvicorn.run` patched, `main()` calls it once with `workers=1`, `timeout_graceful_shutdown=30`, `timeout_keep_alive=65`, and the settings' host and port.
3. Size bound, against `RequestSizeLimit` around a recording app and hand-built ASGI scopes: `content-length` `65536` passes; `65537` is `413` with the constant body byte for byte and the inner app is not called; `content-length` `abc` and `-1` are `413`; `transfer-encoding: chunked` with no `content-length` is `411` with its constant body; `transfer-encoding: chunked` with `content-length: 5` is `411`; a `POST` with neither header passes; a `GET` with neither header passes; a lifespan scope passes.
