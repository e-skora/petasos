## 0. Terms used here

- **Session**: the three tokens and the expiry `POST /session` returns (003 spec 3.19). The app holds exactly one at a time, in memory and in `localStorage`, shared by every tab of the same browser so one visitor spends one mint per hour.
- **Role token**: the token of the current "You are:" selection (Owner, Agent, or Visitor). The app sends it on every read; ticket actions and the guided scenario always send the agent token (7.4).
- **Hold**: the press-and-hold gesture that approves a card: 1.2 seconds for L4, 2.5 seconds for L5 (D-009). The gesture works with a pointer or with the space bar.
- **Pill**: the "N waiting for you" indicator in the top bar. It has exactly three states: unknown, a number, or none waiting (D-014).
- **Guided scenario**: the "Ask for a $42 refund" walk-through on the home screen.
- **Recorded response**: a JSON file under `demo/src/fixtures/`, one per entry of 004's `FIXTURES` map (004 spec test 17), with invented values in the exact shape of that endpoint's response; 004's test compares each committed file with the live API by keys, types, and the fixed enum values, so the app's tests never need a server and a drifted fixture fails CI.
- **Envelope**: the five-key JSON of 004 spec 4.6 (`status`, `explanation`, `tier`, `verb`, `grant_id`, plus `data`). Exception, from the merged 004: a `POST /session` refusal (for example its `429`) carries only `status` and `explanation`, so `api.ts` reads every envelope key except `status` as optional. The one other shape the app reads is the guard seam's `409` (003 spec 3.10), a JSON-RPC error object; `api.ts` maps it into an envelope with `status` `refused/guard_tripped` and `explanation` set to `error.message`.

## 3. Acceptance tests (plain language; each becomes a Vitest test named for it)

Every test runs under Vitest with jsdom, fake timers, and a fake `fetch` that replays recorded responses; no test touches the network, a real clock, or `dist/`.

1. Session: on first load with an empty `localStorage`, exactly one `POST /session` is sent even when three components ask at once (a counting fake fetch); two independent page instances (two module registries via `vi.resetModules`, one shared fake `localStorage`, a fake `navigator.locks` that serialises callbacks, and a delayed fake fetch) that both load on empty storage send exactly one mint between them and end up with the same session; without `navigator.locks` each instance mints once and says nothing; a `storage` event carrying a new session makes the other instance drop its cards and cancel an active hold; a delayed `401` from a request sent under the old session after a replacement is ignored and sends no mint; a `401` for the current session while its stored `expires_at` is still 45 minutes away mints exactly once and never reuses the rejected id; two instances that both receive that session's `401` at the same moment mint exactly once between them and both adopt the replacement; "Start over" on an unexpired session mints exactly once and replaces it in both instances; the tokens land in `localStorage` with `expires_at`; a second load within the hour sends no mint; a stored session under 60 seconds from expiry is replaced by one mint; a `401` on a read mints once more and shows the "Your hour is up" line; a `429` from `POST /session` shows the recorded `explanation` and "Try again" and no further mint is sent until it is clicked; "Start over" sends one mint and clears the old tokens; no token string appears in `location.hash`, in any rendered text, or in any `console` call (spied).

Nothing is known to have happened; check the inbox." and triggers one approvals poll; a `429` on `propose` shows the recorded `explanation`; the inbox on a `403` shows the "We could not check" sentence and no list.
