## Findings, ranked

### 1. Verify the archive before deleting the source rows

blocker | `changes/005-deploy-fly-cloudflare/spec.md:30` | VERIFIED by a focused data probe; the proposed rotation itself is not built.

The pre-delete check compares only the number of rows and the final stored hash. Changing an earlier row's content while leaving its stored hash alone preserves both comparisons. The specification then deletes the source rows, commits a new healthy chain, and only afterwards verifies the archive. A warning at that point cannot restore the original rows. An already-damaged source chain can also become a successful live `verify()` result after rotation.

**Evidence:** Using the actual ledger schema and verifier, I copied a valid ledger, changed row 2's `detail_json` only in the archive, and obtained both `count matches = true` and `last hash matches = true`. `chain.verify(archive)` returned `2`. Thus both specified pre-delete checks can pass with a damaged archive.

**Fix:** Inside the main write transaction, verify the source and the committed archive before deleting anything, and compare their ordered row contents or a digest covering every copied column, including ids. Refuse rotation and preserve the source on any mismatch. Add cases for altered middle content, altered ids, an already-broken source, and a missing row. Keep the existing rollback tests. Also acquire the source lock before deciding whether rotation is needed and create the archive exclusively; cleanup must remove only a file this attempt owns. Test the scheduled tick racing the manual `rotate` command, so one failed attempt cannot delete the other's committed archive.

### 2. The smoke journey can pass without a refund effect

blocker | `changes/005-deploy-fly-cloudflare/spec.md:38` | VERIFIED, reproduced through the pinned MCP client and the 003 application.

The smoke script checks result words, an empty pending list, and refusal of a second approval. It never observes the refund record. Those checks prove that the grant progressed through its states, not that exactly one refund was recorded. This falls short of the promised confirmation that the action executed once.

**Evidence:** In a disposable instance, I replaced only `helpdesk.fake_payments.record_refund` with a function that does nothing. Every predicate in 5.10 still passed: health, mint, role tool lists, ticket amount, staged result, owner card, `executed`, repeat refusal, and empty inbox. The actual `helpdesk_fake_refunds` count was **0**. This was a probe of the proposed acceptance conditions, not execution of a finished smoke script.

**Fix:** Specify a supported way for the release check to read the effect and require exactly one receipt for this action, with the expected ticket, amount and currency, both before and after the repeated approval. Add negative tests that suppress the effect or create two receipts. Settle the interface in planning: either provide a scoped receipt through an MCP read in a prerequisite correction, or make release confirmation depend on 004's ticket-activity read while keeping the two builds separate. Do not leave a 005 builder to invent a read interface outside its file wall. Until then, the script must not claim to prove execution exactly once.

### 3. The $42 journey reuses requests that are not for $42

blocker | `changes/007-demo-app/spec.md:24` | VERIFIED against the 003 gate; the browser consequence is REASONED.

Step 1 reuses any waiting refund on ticket 3. A visitor can first request $1.00 from the editable ticket action or MCP, then press “Ask for a $42 refund.” The rule selects the $1.00 card. It can also select a request proposed by the owner, which that owner cannot approve, or one made against an old ticket version. The test uses only a suitable waiting card, so it misses these cases.

**Evidence:** The actual gate accepted a `1.00` USD refund and returned a pending card with verb `ISSUE-REFUND`, resource `ticket:3`, and `record.amount_minor == 100`. It satisfies the specification's entire reuse predicate.

**Fix:** Reuse only a card matching the intended action: the session's agent proposer, ticket 3, 4200 minor units, USD, and the current ticket version and destination. Choose deterministically if more than one matches. Leave unrelated cards untouched and state what happens if the desired proposal cannot be staged. Add $1.00, owner-proposed, stale-version and multiple-card cases. Outcome text must always come from the selected record, as 7.3 already requires.

### 4. Normal keyboard repeat cancels the keyboard hold

blocker | `changes/007-demo-app/spec.md:25` | REASONED from the rule and the browser event standard.

The specification promises a Space-bar hold but cancels it on repeated `keydown`. A held key normally produces repeat events before a 1.2-second or 2.5-second hold finishes. On such a keyboard the user does exactly what the interface asks and the hold cancels. The fallback button is useful, but it does not make the promised keyboard gesture work. [UI Events defines repeat events for held keys](https://www.w3.org/TR/uievents/#dom-keyboardevent-repeat).

**Fix:** Prevent the default action and ignore repeat events for the already-active Space hold. Do not restart its timer or create a second hold. Keep early release, focus loss and hidden-page cancellation. Update the proposal and test 4, which currently require the broken behavior. Test one initial keydown, several repeat keydowns, then keyup after the required interval, with exactly one approval. Test the same sequence with an early release and require none.

### 5. Session sharing needs coordination between tabs and old requests

should-fix | `changes/007-demo-app/spec.md:22` | REASONED.

A shared promise stops duplicate mints within one page. It does not coordinate two tabs, each with its own JavaScript state, that both read empty or expired storage before either mint finishes. Both can mint and retain different sessions, despite the stated one-session-per-browser rule. There is also no rule for a delayed 401 from the old session after a newer session has already been installed; “on any 401” can mint again unnecessarily. [The HTML standard explicitly warns that local storage has no assumed locking mechanism](https://html.spec.whatwg.org/multipage/webstorage.html#the-localstorage-attribute).

**Fix:** Specify cross-tab mint coordination, re-check storage after obtaining that coordination, and propagate session replacements to open tabs. Associate requests with the session that issued them. Ignore stale responses and stale 401s after replacement, clear old cards, and cancel an active hold when its session or role changes. Give unavailable storage or coordination an explicit fallback. Test two independent page instances with shared storage and delayed responses, not just three components sharing one module promise.

### 6. Correct acceptance cases that contradict authentication and approval

should-fix | `changes/004-owner-api/spec.md:89` and `:95` | VERIFIED by source inspection and an expiry probe.

Test 4 says the fifth approvals read succeeds after advancing 61 minutes. The same session's identity expires after 60 minutes, so authentication correctly returns 401 before reaching the quota check. I confirmed that `ClientRegistry.authenticate` returns `None` at that time. Test 7 also says to “stage and approve `delete_ticket` ... as the owner,” which, read literally, demands the self-approval that test 6 correctly forbids.

**Fix:** Test rolling-window reuse directly at the quota-store layer using a synthetic scope. At HTTP level, assert that the old token remains 401 and a new session can read. In test 7 explicitly stage the deletion as the agent and approve it as the owner. These are small test-description corrections; do not weaken expiry or self-approval to satisfy them.

### 7. The fixture contract does not cover the responses the app relies on

should-fix | `changes/004-owner-api/spec.md:111` and `changes/007-demo-app/spec.md:26` | VERIFIED by comparing the reader journey and required fixtures.

004 test 17 generates responses only from its refund reader journey. That journey contains no email card, populated note or mail list, abort response, guard refusal, or failed verify response. An empty list has no element fields to compare. Key equality alone also accepts a string where the app expects a number. The later promise of a checked fixture for every consumed response therefore exceeds what this test establishes. There is no explicit mapping from fixture filenames to endpoint, role and scenario.

**Fix:** Have 004 define named scenarios and a stable fixture mapping now, including every response variant 007 uses. Generate non-empty collections and all action-card variants. Compare field types and required enum values as well as keys, allowing the documented nullable fields and replacing only designated dynamic values. Require the fixtures when the demo package exists. In 007 CI, changing a nested mail field or changing `amount_minor` from a number to a string must fail the Python contract test, without editing that test in 007's forbidden `tests/` directory.

### 8. Qualify the CI evidence used by the release gate

should-fix | `.github/workflows/deploy-api.yml:67` | VERIFIED inspection; the conflicting-evidence case is REASONED, not an observed release.

The gate reduces checks to name and conclusion, then accepts any matching success line. It discards which app and workflow produced the check and which run it belongs to. If the response contains both a successful namesake and a failed required check, the success wins. It also stops at the first 100 results. A commit id alone does not establish that these three successful names came from this repository's intended CI run. [GitHub's check response includes app and check-suite identity](https://docs.github.com/en/rest/checks/runs#list-check-runs-for-a-git-reference).

**Fix:** Select the intended CI workflow and its latest applicable run on the exact commit, and require all three completed successful jobs from that run. Handle pagination and reject missing or ambiguous evidence. Add planning-owned tests for a missing job, a queued or failed current run, a successful namesake from another producer, and conflicting runs. No change to D-015 is needed.

### 9. Show the destination from the approved record

should-fix | `changes/004-owner-api/spec.md:35` and `changes/007-demo-app/spec.md:25` | VERIFIED inspection; the display risk is REASONED.

Returning the full record to the approver is the right choice. However, the visible email card is required to show only a customer name, ticket/version summary, and body. The destination is available in `record.destination` but need never appear on screen. Customer metadata is read separately from the frozen record. A person can therefore approve without seeing the actual recipient recorded for the action. The card's `subject` is the support-ticket subject, whereas 003's fake mail uses the fixed email subject “A reply to your ticket.” Those labels should not be confused.

**Fix:** Require an explicit recipient line from `record.destination`, keep the ticket subject labelled as ticket context, and identify the fixed outbound subject for email approval. Keep the body as literal text. Test a record whose recipient differs from the ticket's display metadata and require the recorded recipient on the card. This needs no new endpoint or disclosure of a token.

### 10. Make the live-ledger boundary visible after rotation

should-fix | `changes/005-deploy-fly-cloudflare/spec.md:30` and `changes/004-owner-api/spec.md:37` | REASONED across the two specifications.

Rotation removes every row from the live table, including rows belonging to sessions that are still active. The owner ledger reads only that table, and the rotation marker has global scope, so the browser sees neither the moved rows nor the marker. A visitor can complete a refund, cross a rotation, and find its history missing; the guided scenario can also lose its earlier `staged` row between steps. A successful live `verify` covers only the new segment, although the interface says every row checks out.

**Fix:** Specify the retained-history boundary in the browser contract. Either support safe, scoped reads of retained archives, or expose that earlier history was archived and label verification as covering the current segment only. The guided scenario must handle an archived part of its history honestly. Add a combined test that forces rotation between staging and approval, then between approval and ledger viewing. Keep the two build walls intact by defining their shared contract in planning.

## What holds up

- Origin handling belongs outside the guard so it can add browser headers to a guard refusal. The two new constant origin responses can be explicit exceptions; application payloads still belong inside the guard. The existing constant `ServerErrorMiddleware` 500 response from 003 should also remain explicitly acknowledged when the architecture says there are no other exceptions.
- Writing the authenticated identity into the existing request-state dictionary matches the guard's actor/scope lookup. The new routes must continue taking identity, scope, risk and derived verb from server-owned sources. The approval's claimed verb remains comparison-only.
- The shared service extraction is feasible. The card and approve-then-run logic are inline in 003, so the new functions are extractions rather than existing top-level names. The listed compatibility imports can stay intact.
- Charging browser Gate calls and approval actions to the shared `calls` family preserves the existing hourly limit. The separate polling allowance is reasonable. `list_pending` can sweep expired grants, so “polled reads write no ledger row” should mean no new read-event row, not a guarantee of zero expiry writes.
- The unchanged `create_app(db, *, clock)` signature supports 005's wrappers. The named tables, identity fields, quota functions, read capture, grant methods, record conversion, transaction boundary and ledger append/verify interfaces exist at the reviewed 003 head.
- Resetting both session and identity expiry before normal deletion uses the correct authentication boundary and preserves the ordinary cleanup transaction. The constant outer 411/413 responses are explicitly scoped exceptions. I found no additional blocker in those choices.
- I ran the actual merge-gate wall parsers: 004 has 10 expected paths, 005 has 17, and 007 has 3. No expected entry conflicts with its parsed forbidden list. Inspection of the patterns confirms the intended build walls are disjoint. The workflows remain planning-owned.
